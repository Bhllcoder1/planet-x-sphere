## 0. What SPHEREx itself already does (key finding)
- [V: https://arxiv.org/html/2511.15823] Level 2 "Estimate Fine Astrometry": calibrators = good Gaia solution, SNR>10, not saturated, no source within 2 px brighter than 10% of flux. Two stages: Astrometry.net initial solution, then SCAMP, run iteratively. Header keyword FINAST = 0 for images with rms < 1". "Median astrometric alignment precision of images with FINAST=0 reaches 0.1-0.4" on average" (= 0.016-0.065 px at 6.15"/px). Pipeline solves "translation and rotation of the field per image".
- [V: same] L3 uses "per-detector distortion map calibration FITS images" as separate input. So whether the IMAGE-HDU WCS itself carries full distortion (SIP) is [NV]; the data-products page does not mention SIP for the spectral image (grep: none). Check the real header for A_ORDER/-SIP in CTYPE before assuming.
- [V: same] Planned improvement list includes fixed distortion from many images; images with bad astrometry exist (FINAST != 0 are not transferred to IRSA per DQ rule: "fine astrometry flag value of 0" required).
- Implication [inference]: an independent re-solve will not beat 0.1-0.4"; the useful product is a per-frame residual check vs Gaia (shift +/- rotation) and reporting it, which matches PLAN T5.

## 2. Detection and PSF fitting
- SEP [V: https://sep.readthedocs.io/en/stable/reference.html]: Background (mask, bw...), extract(data, thresh, err, mask,...), winpos(data, xinit, yinit, sig, mask) "more accurate centroids, windowed algorithm"; (0,0) = centre of first pixel (0-based, differs by -1 from SExtractor/FITS); flags OBJ_MERGED etc. No PSF model, no variable PSF. Pure CPU C, fast. GPU: none stated [NV].
- photutils detection [V: https://docs.astropy.org/projects/photutils/en/stable/user_guide/detection.html (listing)]: DAOStarFinder, IRAFStarFinder, StarFinder (image-kernel; could use SPHEREx ePSF as kernel [inference]), find_peaks; centroids: centroid_com/1dg/2dg/quadratic/symmetry. DAO/IRAF assume Gaussian kernel with FWHM; accuracy numbers not on the page.
- PSF photometry [V: https://photutils.readthedocs.io/en/stable/user_guide/psf.html]: PSFPhotometry(psf_model, fit_shape, ...), grouper (SourceGrouper), local_bkg_estimator, small fit_shape e.g. (5,5). Image-based models ImagePSF and GriddedPSFModel interpolate the input image and do not integrate it over pixels; input MUST be an ePSF (flux in whole pixel centred at offset), not an optical PSF; for undersampled data a sampled PSF is wrong because the sum over pixels changes with subpixel position. Oversampled ePSF values sum to oversampling^2 (ImagePSF requirement). FWHM < ~2 px counts as undersampled (page text).
- GriddedPSFModel [V: https://photutils.readthedocs.io/en/stable/api/photutils.psf.GriddedPSFModel.html via search snippet + page fetched]: grid of ePSFs at fiducial positions that must form a rectangular grid; bilinear interpolation between them; meta needs grid_xypos and oversampling. SPHEREx EPSF zones: 21x21 (detectors 1,2,4,5,6), 11x41 (detector 3), each 33x33 oversample 5 [V: https://caltech-ipac.github.io/spherex-archive-documentation/spherex-data-products]. Tutorial table has XCENTER/YCENTER/BINX/BINY, OVSMPX=5, 441 rows, 33x33 [V: https://caltech-ipac.github.io/irsa-tutorials/spherex-psf/]. This RESOLVES the PLAN S0.5 conflict: EPSF HDU is oversampling 5, 33x33 (covers 5x5 native px ~30"); the 0.615"/10x, 101x101 numbers are the older QR2 PSF HDU (121 planes, 11x11 grid) [V data-products page]. Docs recommend ePSF for all images [V]. Tutorial imports photutils ImagePSF [V].
- Zone index: data-products page says (QR2 PSF) pick plane via XCTR_i/YCTR_i; the ePSF uses table columns XCENTER/YCENTER [V]. Cutout->parent conversion uses CRPIX1A/2A with a +1 [V page text lines ~144-162; exact semantic still to test, as PLAN S0.6].
- Spatial-variation handling: GriddedPSFModel interpolates between zones bilinearly [V snippet]; wavelength dependence: ePSF table has CWAVE/CBAND columns and a per-detector calibration file [V tutorial]; whether the ePSF in an image is already for that image's band/zone is [NV].
- Pixel-phase / undersampling: Anderson & King 2000 define pixel-phase error as systematic positional error in undersampled images depending on position relative to pixel boundaries; an accurate ePSF removes it; precision 0.02 px single star, systematic <0.002 px [V: https://ar5iv.arxiv.org/html/astro-ph/0006325]. A later study (search snippet only) says that library not always sufficient across epochs [NV].
- GPU: SEP/photutils CPU-only in the pages read [NV for absence]. Candidates seen only in search snippets: GPUPhot (CuPy) [NV: pypi page blocked; paper id in snippet looked unreliable], GPU-SExtractor (C/CUDA 2013, ~6x), POPPY CuPy (optics only). Recommendation [inference]: no GPU needed: 2040x2040 SEP extract takes ~ seconds (timing NV); fitting few-hundred stars with 5x5 stamps is cheap. Write own vectorised batched Gauss-Newton on ePSF stamps (numpy/torch) if thousands of sources.

- SPHEREx already flags [V: https://caltech-ipac.github.io/irsa-tutorials/spherex-intro header listing]: NONLINEAR, PERSIST, HOT, COLD, TRAN_NB, PERS_NB, SOURCE, XTALK, GHOST, GHOST_FPA, GHOST_EXT, BLOOM(_NS), SNOW(_NS), OUTLIER, TRANSIENT, OVERFLOW, SUR_ERROR, NONFUNC, DICHROIC, MISSING, FULLSAMPLE, PHANMISS, SNOWBALL, HALO (transient halo), SAT_HALO. - [V: arxiv html 2511.15823] on-board transient detection (Level 0); Level 2 "Detect Outlier Pixels": sigma clipping on median-filtered images, added to FLAGS; image rejected if transient count >435,000 px; pipeline paper lists future: "improved flagging for transients incl. satellites and extended cosmic rays" => extended CR / satellite trails are NOT fully flagged today. Persistence modelled and flagged; crosstalk/ghosts/frame edge ghosts partly masked, improvements planned.
- astroscrappy [V: https://astroscrappy.readthedocs.io/en/latest/api/astroscrappy.detect_cosmics.html]: detect_cosmics(indat, inmask, inbkg, invar, sigclip=4.5, sigfrac=0.3, objlim=5.0, gain, readnoise, satlevel, niter=4, ..., psfmodel in gauss/gaussx/gaussy/moffat, psffwhm...) returns crmask + cleaned array. L.A.Cosmic is based on Laplacian edge detection and assumes PSF broader than CR (i.e. well-sampled) [inference/NV: not stated on page]. On an undersampled PSF (FWHM ~ 1-2 px) it can eat star cores [inference, NV]; so: never replace pixels, only use as extra mask, and exclude pixels within SOURCE-flagged/Gaia-star neighbourhoods; or test by injection (PLAN T3). Units: input is MJy/sr, not electrons; gain/readnoise settings need care [inference].
- Simple robust approach [inference]: reject per-star fit pixels with |resid|/sigma > ~4-5 after first fit, refit (iterative); FLAGS mask for the rest; SOURCE bit is not a defect.

## 4. Centroid uncertainty
- Cramer-Rao bound is the floor on variance for unbiased estimators; Mendez et al. studied dependence on position, intensity, SNR, resolution (only via search snippet; paper not fetched) [NV].
- [V: https://arxiv.org/abs/1610.05873] Vakili & Hogg: compares centroiders to CRLB vs SNR and FWHM; zero-mean constant Gaussian noise assumed; exact-PSF fitting reaches the bound (snippet), centre-of-light does not [abstract does not state; snippet NV].
- [V: https://arxiv.org/abs/2004.06253] Lin et al.: ePSF vs Gaussian centering; precision difference depends on star profile. The factor "8/(3 sqrt3)" from PLAN came from a snippet, still NV.
- [V: https://ar5iv.arxiv.org/html/1509.00677 and arxiv.org/abs/1805.03673] Lobos/Espinosa et al.: least-squares/ML estimators generally cannot reach the CRB exactly, gap characterised; analysis assumes idealised 1-D array, no intra-pixel response variation (snippet) [NV on the latter].
- Practical recipe [inference]: sigma from Fisher matrix of the ePSF model with real VARIANCE: I_xx = sum_i (dM_i/dx)^2 / var_i, sigma_x = I^-1 sqrt (with flux and background marginalised via full 4x4 matrix). Compare with empirical injection RMS (PLAN T3) and Gaia residuals; floor with a systematic term (Anderson-King 0.002 px best case; SPHEREx WCS 0.016-0.065 px per frame [V pipeline paper]).

## 5. What makes "exactly 1 px shift" hard
- Pixel convention: astropy origin 0 vs 1 (origin = coordinate of the upper-left pixel; FITS 1, numpy 0) [V: https://docs.astropy.org/en/stable/api/astropy.wcs.WCS.html]; fit_wcs_from_points wants FITS 1-based xy [V]; SEP is 0-based (0,0) = centre of first element [V]; photutils uses 0-based [NV from these pages].
- SIP inverse: astropy all_world2pix uses numerical iteration to invert the full forward transform incl. SIP; params in the stable page: tolerance=1e-4 (px), maxiter=20, adaptive=False, detect_divergence=True, quiet=False [V]. Default 1e-4 px is OK, but set tolerance explicitly. wcs_world2pix ignores SIP [V: note_sip page says wcs_pix2world/world2pix ignore distortion]. Approximate AP/BP inverse: accuracy not quantified in fetched pages [NV].
- With SIP, a world shift does not equal a constant pixel shift: local scale/rotation vary across the 2040 px field; frames with different roll give a rotated pixel grid. "1 px" is only exact in the native pixel frame of one image or in a locally affine frame (PLAN 2.3).
- Undersampling: pixel-phase bias can displace measured centroids with a non-1 px artefact when comparing two frames with different sub-pixel phases and different wavelengths (PSF changes) [Anderson-King V + inference]; only a correct per-zone, per-band ePSF removes it.
- Different bands in different frames => different PSF and possibly chromatic centroid shift [inference].
- Per-frame WCS accuracy 0.1-0.4" [V] means two frames' absolute positions agree to ~0.02-0.07 px at best, so "exactly 1.000 px" must be verified on injected synthetic shifts (T1), not via sky WCS.
